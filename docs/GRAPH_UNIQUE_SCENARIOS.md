# Graph 고유 질의 시나리오 — Databricks Genie 차별화

> **목적**: SQL(Genie)로는 답변이 불가능하거나 품질이 현저히 떨어지는, Graph DB만의 유즈케이스
> **기준**: 현재 데이터 모델(Employee, Skill, Project, Department, Concept, Certificate, Position, Location) + GDS 알고리즘 기반
> **Last Updated**: 2026-03-11

---

## 난이도 범례

| 등급 | 의미 | SQL 가능 여부 |
|------|------|-------------|
| ★★★ | Graph 필수 — SQL로 표현 불가 | 불가능 |
| ★★☆ | Graph 강력 우위 — SQL로 가능하나 매우 복잡하고 성능 열악 | 이론적 가능, 실용적 불가 |
| ★☆☆ | Graph 우위 — SQL보다 자연스럽고 정확 | 가능하나 열등 |

## Tier 1. 경로 탐색 — "연결"을 묻는 질문 ★★★

> **핵심**: 가변 길이 경로(variable-length path)는 SQL의 recursive CTE로는 깊이·성능 한계

### 질의 1-1. 두 사람의 연결 경로

```
"김철수와 박지우는 어떤 경로로 연결되어 있어?"
```

**Graph 답변**: 김철수 →(WORKS_ON)→ AI 추천엔진 ←(WORKS_ON)← 이민수 →(MENTORS)→ 박지우
- 중간 노드(프로젝트, 사람)까지 시각화
- shortestPath 알고리즘으로 최단 경로 자동 탐색

**Genie**: 두 사람이 같은 프로젝트에 있는지 1-hop만 JOIN 가능. 2-hop 이상 경로는 사실상 불가.

### 질의 1-2. 팀 간 브릿지 인물

```
"개발1팀과 데이터팀을 연결하는 브릿지 인물은 누구야?"
```

**Graph 답변**: 두 부서 사이를 프로젝트 공동 참여 또는 멘토링 관계로 이어주는 사람 탐색
```cypher
MATCH (d1:Department {name:'개발1팀'})<-[:BELONGS_TO]-(bridge)-[:BELONGS_TO]->(d2:Department {name:'데이터팀'})
// 또는 프로젝트 경유:
MATCH (d1)<-[:BELONGS_TO]-(e1)-[:WORKS_ON]->(p)<-[:WORKS_ON]-(e2)-[:BELONGS_TO]->(d2)
```

**Genie**: 부서 간 직접 이동자만 찾을 수 있음. 프로젝트 경유 간접 연결은 다중 self-JOIN 필요.

### 질의 1-3. 지식 전파 경로

```
"RAG 기술이 어떤 경로로 우리 조직에 퍼졌어?"
```

**Graph 답변**: RAG 스킬 보유자들의 프로젝트 참여 이력 → 동료에게 전파 → 멘토링으로 확산된 경로를 타임라인으로 시각화
```cypher
MATCH path = (early:Employee)-[:HAS_SKILL]->(:Skill {name:'RAG'}),
      (early)-[:WORKS_ON]->(p)<-[:WORKS_ON]-(later:Employee)-[:HAS_SKILL]->(:Skill {name:'RAG'})
WHERE early.hire_date < later.hire_date
```

**Genie**: 시간 순서 + 관계 경유 경로 조합은 SQL로 표현 자체가 극히 어려움.

## Tier 2. 그래프 알고리즘 — "구조"를 묻는 질문 ★★★

> **핵심**: Centrality, Community Detection, PageRank 등은 SQL에 동등한 개념 자체가 없음

### 질의 2-1. 조직의 지식 병목 (Single Point of Failure)

```
"퇴사하면 가장 큰 영향을 미치는 직원 Top 5는?"
```

**Graph 답변**: Betweenness Centrality — 많은 최단 경로가 경유하는 노드 = 지식 병목
- "이 사람이 빠지면 A팀-B팀 간 연결이 끊깁니다"
- 영향 범위(연결된 프로젝트 수, 멘티 수, 유일한 스킬) 함께 제공

**Genie**: 프로젝트 수나 스킬 수로 COUNT 정렬은 가능하지만, "구조적 중요도"는 판단 불가.

### 질의 2-2. 자연스러운 팀 클러스터

```
"스킬 유사성 기반으로 우리 조직의 자연스러운 팀 구분은 어떻게 돼?"
```

**Graph 답변**: Leiden 커뮤니티 탐지 → 스킬 유사도 기반 자동 클러스터링
- "커뮤니티 A: ML 중심 (15명), 커뮤니티 B: 풀스택 웹 (12명), 커뮤니티 C: 인프라/DevOps (8명)"
- 현재 부서 구조와 스킬 클러스터의 불일치(mismatch) 발견 가능

**Genie**: 스킬을 피벗 테이블로 만들어 클러스터링하려면 별도 ML 파이프라인 필요. SQL만으로 불가.

### 질의 2-3. 핵심 기술 (구조적 중심성)

```
"우리 조직에서 가장 핵심적인 기술은? (단순 보유자 수가 아니라 프로젝트 연결도 기준)"
```

**Graph 답변**: Skill 노드의 Degree Centrality × PageRank 복합 점수
- Python: 보유자 45명 × 12개 프로젝트 연결 = 핵심도 1위
- "Python이 빠지면 영향받는 프로젝트 12개, 직원 45명"
- 단순 COUNT와 다른 점: 프로젝트-직원-부서 간 간접 연결까지 고려

**Genie**: `COUNT(*)` 정렬만 가능. 간접적 영향력(2-hop, 3-hop)은 계산 불가.

## Tier 3. 온톨로지 추론 — "유사성"을 묻는 질문 ★★☆

> **핵심**: IS_A 계층 탐색 + 동의어 확장 → SQL의 단순 문자열 매칭과 차원이 다른 검색

### 질의 3-1. 스킬 전이 가능성 (빠른 습득 예측)

```
"Pinecone 기술을 가장 빠르게 습득할 가능성이 높은 인원은?"
```

**Graph 답변**: 온톨로지 계층에서 Pinecone의 형제/사촌 노드 탐색
```
Pinecone IS_A Database(VectorDB)
  형제: ChromaDB, Weaviate  ← 이 스킬 보유자 = 즉시 전환 가능
  사촌: Elasticsearch (같은 Database 하위) ← 검색 패러다임 유사
  선수: Python (AI/ML + Database 공통) ← 기본 요건
```
→ ChromaDB + Python 보유자를 1순위로 추천, 근거와 함께 제공

**Genie**: "Pinecone" 문자열 매칭만 가능. 유사 기술 관계를 모르므로 "ChromaDB 보유자가 빠르게 배울 수 있다"는 추론 불가.

### 질의 3-2. 의미 확장 검색

```
"머신러닝 관련 스킬 보유자 전체 목록"
```

**Graph 답변**: Concept 계층 자동 탐색
```
"머신러닝" (동의어: ML, Machine Learning, 기계학습)
  └─ IS_A → AI/ML
       └─ 하위: TensorFlow, PyTorch, Scikit-learn, NLP, Computer Vision,
                Fine-tuning, RAG, Hugging Face, MLflow, Kubeflow, OpenAI API
```
→ 12개 하위 스킬 보유자 모두 자동 포함 (직접 "ML" 태그가 없어도)

**Genie**: "ML" 컬럼 매칭만 가능. TensorFlow 보유자가 ML 관련인지 모름. 수동으로 WHERE skill IN ('ML', 'TensorFlow', ...) 나열 필요.

### 질의 3-3. 크로스 도메인 인재

```
"백엔드와 AI/ML 양쪽 모두 경험 있는 풀스택 AI 엔지니어는?"
```

**Graph 답변**: 온톨로지에서 Python, TypeScript는 Backend + AI/ML 양쪽에 속함 (크로스 도메인)
→ Backend 하위 스킬 ∩ AI/ML 하위 스킬을 동시 보유한 직원

**Genie**: 스킬 카테고리가 테이블에 있다면 가능하지만, "Python이 Backend이면서 동시에 AI/ML"이라는 다중 분류 관계는 RDB에서 표현하기 어려움.

## Tier 4. 복합 관계 추론 — "네트워크 효과"를 묻는 질문 ★★☆

> **핵심**: 2-hop 이상의 관계 체인 + 집계의 조합

### 질의 4-1. 협업 네트워크 기반 추천

```
"추천시스템 고도화 프로젝트 핵심 개발자와 과거 협업 경험이 있는 인원은?"
```

**Graph 답변**:
```
추천시스템 고도화 ←(WORKS_ON)─ 핵심개발자들
  각 핵심개발자 ─(WORKS_ON)→ 과거 프로젝트들
    과거 프로젝트 ←(WORKS_ON)─ 협업 경험자들 (추천 대상)
```
3-hop 탐색: Project → Employee → Other Projects → Other Employees
+ 협업 횟수(공유 프로젝트 수)로 친밀도 스코어링

**Genie**: 3중 self-JOIN으로 이론적 가능하나, 성능·가독성 모두 열악. "협업 횟수" 집계까지 추가하면 SQL이 매우 복잡.

### 질의 4-2. 멘토링 체인 영향력

```
"김철수의 멘토링 네트워크에서 영향을 받은 전체 인원과 그들의 스킬 분포는?"
```

**Graph 답변**:
```
김철수 ─(MENTORS)→ 멘티1, 멘티2
  멘티1 ─(MENTORS)→ 멘티1-1, 멘티1-2  (2차 멘티)
    멘티1-1 ─(MENTORS)→ ...           (3차 멘티)
```
가변 길이 경로: `(김철수)-[:MENTORS*1..3]->(mentee)` 로 전체 멘토링 트리 탐색
→ 각 깊이별 인원 수, 전체 스킬 분포 집계

**Genie**: recursive CTE로 1-2단계는 가능하나, 가변 깊이 + 스킬 집계 조합은 SQL이 매우 고통스러움.

### 질의 4-3. 프로젝트 유사도 기반 경험자

```
"추천시스템 고도화 프로젝트와 기술 스택이 가장 유사한 프로젝트 경험자는?"
```

**Graph 답변**: 프로젝트 간 공유 REQUIRES 스킬로 Jaccard 유사도 계산
```
추천시스템 고도화 REQUIRES [Python, Pinecone, Kubeflow, Angular, RAG]
AI 추천엔진     REQUIRES [Python, TensorFlow, Kubeflow, RAG]
  → Jaccard = |{Python, Kubeflow, RAG}| / |합집합| = 3/6 = 0.5
```
→ 유사도 Top 3 프로젝트의 참여자 중, 추천시스템 고도화에 미투입된 인원 추천

**Genie**: 프로젝트별 스킬을 피벗 → 유사도 계산 → 참여자 필터링의 3단계를 SQL로 작성해야 함. 이론적 가능하나 매우 복잡.

## Tier 5. 시각화 + 구조적 인사이트 — "보여줘" 질문 ★★☆

> **핵심**: 답변이 "테이블"이 아니라 "그래프"여야 의미가 있는 질문

### 질의 5-1. 부서 간 협업 네트워크

```
"부서 간 협업 관계를 시각화해줘"
```

**Graph 답변**: 부서 노드 간 프로젝트 공유 관계를 가중치 그래프로 시각화
- 엣지 두께 = 공유 프로젝트 수
- 고립된 부서(island) 즉시 발견
- "개발1팀-데이터팀은 5개 프로젝트 공유, 인프라팀은 고립"

**Genie**: 숫자 테이블로는 줄 수 있지만, 구조적 패턴(고립, 허브, 브릿지)을 한눈에 보여주지 못함.

### 질의 5-2. 스킬 생태계 맵

```
"우리 조직의 스킬 생태계를 보여줘"
```

**Graph 답변**: Concept IS_A 계층 + Skill 보유자 수를 노드 크기로 시각화
- 클러스터: Programming(Backend, Frontend, AI/ML), Infrastructure(Cloud, DevOps)
- 취약 영역(보유자 적은 스킬)이 시각적으로 드러남
- 온톨로지 계층을 인터랙티브하게 탐색

**Genie**: 카테고리별 COUNT 테이블만 제공. 계층 구조와 관계를 시각적으로 보여줄 수 없음.

## AI Day 데모 추천 시나리오 (5개 선별)

> 임팩트 + 현재 구현 완성도 + Genie 대비 차별화를 기준으로 선별

| 순서 | 질의 | 카테고리 | 차별화 포인트 |
|------|------|---------|-------------|
| 1 | "김철수와 박지우는 어떤 경로로 연결되어 있어?" | 경로 탐색 | 시각적 임팩트 최고, SQL 완전 불가 |
| 2 | "퇴사하면 가장 큰 영향을 미치는 직원 Top 5는?" | 그래프 알고리즘 | 경영진 관심사와 직결, SQL 불가 |
| 3 | "머신러닝 관련 스킬 보유자 전체 목록" | 온톨로지 추론 | 같은 질문에 Genie는 ML만, Graph는 12개 하위 스킬 자동 포함 |
| 4 | "스킬 유사성 기반으로 우리 조직의 자연스러운 팀 구분은?" | 커뮤니티 탐지 | 부서 구조 vs 실제 스킬 클러스터 비교 — HR 인사이트 |
| 5 | "추천시스템 고도화 프로젝트와 기술 스택이 가장 유사한 프로젝트 경험자는?" | 복합 관계 | Genie도 시도하지만 Graph가 압도적으로 정확 |

### 데모 스토리라인 제안

```
[도입] "Genie로 할 수 있는 질문 — 우리도 합니다"
  → 기존 질의 세트 중 1-2개를 양쪽에서 동시 시연

[전환] "하지만 이런 질문은 Genie가 못 합니다"
  → 시나리오 1 (경로 탐색): 그래프 시각화와 함께 wow 효과
  → 시나리오 2 (지식 병목): "이 사람이 퇴사하면?" — 경영진 공감

[심화] "같은 질문도 Graph는 더 똑똑합니다"
  → 시나리오 3 (온톨로지): "ML 보유자" 검색 비교 — recall 차이 명확
  → 시나리오 4 (커뮤니티): 조직 구조 vs 실제 스킬 클러스터 비교

[마무리] "Graph는 관계와 구조에서 인사이트를 뽑습니다"
  → 시나리오 5 (복합 추천): 프로젝트 유사도 + 인력 추천 — 실무 활용
```

| 1-2. 브릿지 인물 | ⚠️ Cypher 생성 가능하나 intent 미분류 | `relationship_search`로 라우팅 되는지 검증 |
| 1-3. 지식 전파 | ❌ 시간 기반 경로 미구현 | 타임라인 시각화 추가 필요 |
| 2-1. 지식 병목 | ⚠️ GDS Betweenness 미구현 | `gds_service.py`에 centrality 추가 필요 |
| 2-2. 팀 클러스터 | ✅ Leiden 커뮤니티 탐지 구현 완료 | 부서 구조와 비교 뷰 추가 |
| 2-3. 핵심 기술 | ⚠️ 파이프라인으로 COUNT는 가능 | PageRank 기반 점수 추가 필요 |
| 3-1. 스킬 전이 | ⚠️ ConceptExpander 있으나 "형제 노드" 탐색 미구현 | 온톨로지에 형제 관계 탐색 로직 추가 |
| 3-2. 의미 확장 | ✅ ConceptExpander + synonyms.yaml | 동작 검증, 데모 시나리오 준비 |
| 3-3. 크로스 도메인 | ✅ schema.yaml에 크로스 도메인 정의됨 | 쿼리 프롬프트에 활용 강화 |
| 4-1. 협업 추천 | ⚠️ relationship_search로 가능하나 스코어링 없음 | 협업 횟수 기반 스코어링 추가 |
